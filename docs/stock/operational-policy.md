# 運用ポリシー

> 本書はプロジェクト運営上の恒久的な原則・方針を集めた stock ドキュメント。
> 個別の手順・SOP は flow ドキュメントや runbook 側で扱う。本書は **What を決めるか・どこで判断するか** を示す。

## 1. データ保持・GC

### 1.1 論理削除と物理削除
- ユーザー操作による削除は **論理削除**（`deletedAt` の設定）で表現する。
- 論理削除されたレコードは原則 **90 日経過後に物理削除候補** となる。物理削除は運用バッチで実施する。
- ユーザーが 90 日以内に「ゴミ箱」相当の機能から復元できる UI を提供することを v1.x で検討する（v1.0.0 ではバックエンドのみ対応）。

### 1.2 永続保持
- `StockEvent` は **永続保持**。消費・廃棄・移動の履歴は分析・監査のため削除しない。
- 容量負荷が問題化した場合の集計・コールドストレージ移行は v1.x の課題。

### 1.3 退会・グループ削除時のデータ
- **ユーザー退会時**: 当該ユーザーの個人プロフィール情報は削除。グループ内の操作履歴（`StockEvent.actorUserId` 等）は **匿名化（`actorUserId` を nil にし、表示名を「退会済みユーザー」とする）** して残す。
- **グループ削除時**: OWNER が明示的に削除した場合のみ。所属する全 `Membership` `Stock` `StockEvent` `RequirementSetting` `ShoppingListItem` `Item`（`ProductMaster` は除く）は論理削除し、90 日後の物理削除対象とする。
- **メンバー削除時**: 当該ユーザーの `Membership` のみ削除。グループ内のデータは保持される。

## 2. プライバシー

### 2.1 データの論理分離
- ユーザーデータは **`groupId`（または `userId`）単位で論理分離** する。グループ外への漏洩を防ぐ。
- `ProductMaster` のみグローバル共有。これは個人情報を含まない公開商品情報のため。

### 2.2 取得・保持する個人情報
- 認証用: メールアドレス、表示名、パスワード（ハッシュ化保存）。
- 任意: アバター画像、ロケール設定、push トークン。
- 在庫情報: 商品名・数量・期限・場所・備考（個人の所有物情報として扱う）。

### 2.3 第三者提供
- 外部 JAN API への問い合わせは **JAN コード（公開情報）のみ送信**。ユーザー個人情報は送信しない。
- 通知配信（push）はプラットフォーマー（Apple / Google）経由で送信される。送信内容は最小限に抑える（タイトル・本文・在庫 ID 程度）。

### 2.4 招待リンク
- 招待リンクには **有効期限** と **使い切り設定** を必須とする（無期限・無制限は禁止）。
- 招待トークンは難読化された URL-safe な乱数（実装は flow ドキュメントで詰める）。

## 3. セキュリティ

### 3.1 認証
- ユーザー認証必須。匿名利用は v1.0.0 では不可とする。
- パスワード認証 + ソーシャル認証（Google / Apple）を最低ラインとする想定。具体採用は実装フェーズで決定。

### 3.2 通信
- すべての API 通信は **HTTPS 必須**。
- 自己署名証明書・有効期限切れ証明書は不可。

### 3.3 暗号化（at rest）
- DB レベルでの暗号化（マネージドサービスの既定機能を利用）。
- 個別レコードの暗号化は v1.0.0 では行わない（バックエンド選定後に再評価）。

### 3.4 監査ログ
- ロール変更・グループ削除・メンバー削除は **監査ログを永続保持** する（実装は flow ドキュメントで詰める）。

## 4. 通知

### 4.1 既定値
- **期限近接通知**: 既定 7 日前に発火。ユーザーは 1〜30 日の範囲で前倒し日数を変更可能。
- **期限切れ通知**: 既定 ON。
- **不足検知通知**: 既定 ON。
- **招待通知**: 既定 ON。

### 4.2 配信頻度の上限
- 同種の通知が短時間に大量発火しないよう、**1 ユーザーあたり 1 時間に同種通知 3 件まで** を目安とする（実装は flow ドキュメントで詰める）。

### 4.3 オフライン時の挙動
- ローカルスケジューラで期限近接通知のみ発火可能（screen-flow.md 6 章参照）。
- サーバ起点の通知（招待・不足検知）はオンライン復旧時に届く。

## 5. データの可搬性

### 5.1 エクスポート
- ユーザーは **自身が所属するグループの在庫・履歴を CSV / JSON でエクスポート** 可能（CLI または Web で）。
- エクスポート対象は閲覧権限を持つデータに限る（VIEWER でも在庫一覧はエクスポート可能、編集ログ詳細は EDITOR 以上）。

### 5.2 インポート
- CSV / JSON 形式でのインポートを CLI で提供。
- インポート時は新規登録のみとし、既存レコードの上書きは行わない（v1.0.0）。

## 6. サービスレベル方針

### 6.1 可用性目標（暫定）
- 月間稼働率 **99.5%** を目標。実測は運用開始後に再設定。
- 災害時のオフライン参照（requirements.md 5.3）が **MUST** であるため、オンライン側の SLA とは別に「直近同期分の参照可」を保証する。

### 6.2 データ損失耐性
- バックアップ頻度は **日次** を最低ラインとする。
- リストアテストは **四半期に 1 回** を目標（実装後に runbook 側で詳細化）。

## 7. ライセンス・法令

### 7.1 個人情報保護法
- 日本国内ユーザーを主対象とするため、個人情報保護法に準拠する。
- プライバシーポリシー・利用規約は v1.0.0 リリースまでに法務的な確認を経た上で公開する（flow ドキュメント / 別資料）。

### 7.2 外部 API 利用規約
- 採用する外部 JAN API（Yahoo!ショッピング・楽天等）の利用規約に従う。
- **キャッシュ可否** と **クレジット表記** は採用前に明文化された結論を残す（jan-api-candidates.md 6 章）。

## 8. 開発・リリースの原則

### 8.1 ドキュメンテーション
- 要件・設計が変動する間は flow ドキュメント（`docs/flow/<version>/`）で扱う。
- 確定した恒久ルールは stock ドキュメント（`docs/stock/`）に集約する。
- ドキュメントは markdown で残す。会話・口頭合意のみでの確定はしない。

### 8.2 スキーマファースト
- DB スキーマ・型定義・API スキーマを先に確定し、実装をそれに従わせる（CLAUDE.md グローバル方針と一致）。

### 8.3 コミット・PR
- Conventional Commits（`feat:` / `fix:` / `docs:` 等）を採用。
- PR の差分が 2000 行を超えそうな場合は分割を検討する。
